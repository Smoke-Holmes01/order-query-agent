# 电商经营分析工作流助手：面试说明

这是一个使用固定模拟数据的受限工具型经营查询 Agent。模型将自然语言转换成结构化计划，程序校验后选择固定 SQL 模板，以专用只读账号查询 MySQL，最后确定性地格式化结果。它只支持每日销售、品类销售和商品排行，不能据此描述为通用 NL2SQL 或完整 BI 平台。

当前实际完成的测试、模式、版本和外部依赖缺口以 [verification.md](verification.md) 为准；[evaluation.mock.json](evaluation.mock.json) 是固定用例评测报告。本文描述设计取舍，不以设计存在代替验收通过。

## 为什么使用固定模板

项目的问题范围很小，主要需要稳定口径、可解释过程和明确权限。让模型选择三类查询、填写日期和排名参数，比接受任意 SQL 更容易做严格校验，也能展示一个完整可验证的工作流。

模型输出五个固定计划字段，不包含表名、列名、排序表达式或连接参数。程序只选择固定 SQL；销售额和销量排行分别对应固定分支，所有外部值用 `%s` 绑定。用户要求删除、自由 SQL 或额外筛选时返回不支持，不把原问题缩减成一个可执行但意思不同的查询。

代价是表达能力受限。增加查询能力需要明确新口径、模板、校验、测试和评测，不会因为模型能生成某段 SQL 就自动开放执行。

## 为什么还使用 LangGraph

这条工作流包含几种实质不同的分支：计划格式错误最多再请求一次；业务缺参进入澄清；不支持的意图直接拒绝；合法计划才查询数据库；供应商和数据库失败立即结束。LangGraph 将这些分支和状态更新明确组织起来，便于观察节点结果及每步耗时。

state 由服务端为每次请求创建，记录 request_id、解析次数、候选/合法计划、查询模板、真实 rows、错误和 trace。客户端只有 question 字段，不能上传执行状态。请求之间没有记忆，不使用 checkpointer。项目也没有多 Agent 或自动数据库错误修复。

四个主节点是 `parse_plan → validate_plan → execute_query → format_answer`。格式重试只属于模型输出校验；数据库失败不会触发重试、改账号或放宽查询限制。同步路由将图和 PyMySQL 放在 FastAPI 的工作线程中执行。

## 为什么追问而不猜

“卖得最好”可能指销售额，也可能指销量；“到10月4日”也可能包含或排除当天。猜测能产生形式合法的查询，却可能回答另一个问题，因此缺口径、缺数量、缺日期或结束边界不明确时应澄清，并保证不执行业务查询。

用户明确“包含结束日期”时，将结束日期转换为下一天，仍统一使用排他上界，并在响应中显示实际区间。相对日期暂未实现可靠解释，要求提供完整年月日。跨度超过90天或 N 超过10时要求调整，不静默截断。

澄清不会创建服务端对话记忆。用户需要把原问题和补充条件一起重新提交，避免把另一次请求的上下文误用到当前请求。

## 金额和时间边界怎样保证正确

历史销售额使用订单明细中的成交单价，不能使用商品当前价格。MySQL 的 `DECIMAL(12,2)` 单价参与求和，PyMySQL 返回 `Decimal`；Python 不经过 float，响应金额固定为两位小数字符串。销量按商品件数求和并序列化为整数。

支付时间字段为 `DATETIME(6)`，本项目约定值是 Asia/Shanghai 当地时间。应用生成当地零点参数，并设置连接会话时区为 `+08:00`。`DATETIME` 本身没有时区属性，不能说数据库自动完成了时区转换。

所有查询统一 `paid_at >= start AND paid_at < end`，仅含 paid 订单。固定模拟记录包含零点、上界前一微秒、上界零点、NULL 支付时间及取消订单，可核对这些边界。区间 `[2026-10-01,2026-10-04)` 人工计算总额500.00，每日为340.00和160.00；10月3日无符合记录，不补零。应用结果仍必须来自真实 SQL 查询，不能返回这些预存常量。

## 参数化、只读权限与超时如何配合

参数绑定将日期和 N 作为数据传入，固定模板约束结构；专用运行账号仅拥有三张演示表的 SELECT，即使应用校验出现错误，数据库权限仍限制写操作。连接检查当前账号、角色与完整授权，发现额外全局、写入或DDL权限就拒绝继续。只读事务是额外措施，不能替代最小权限。

管理员配置只进入初始化和 seed 路径，运行时不读取 `.env.admin`，不会在连接失败后回退到管理员。初始化先检查明确库名白名单、连接目标及已有对象，冲突保留现场；seed 在事务中核对固定主键，只插入缺项，不需要破坏性重建。

日期跨度、N、返回行数和并发数各自控制不同成本。LIMIT 只限制结果数量，不能保证扫描和排序成本，因此还设置 MySQL 服务器 `max_execution_time`。默认一个服务进程最多4个数据库连接，使用单worker；品类超过100行要求缩小范围。

客户端 `read_timeout` 是停止等待服务器响应，不能据此宣称服务器查询被中止。真正的服务器执行限制需要在隔离演示库中用受控只读查询验证，并观察 MySQL 错误3024；客户端socket超时不算通过。权限验收先检查授权，再用 `WHERE 1=0` 的合法写语句测试权限拒绝，且核对前后数据一致，不拿真实seed记录做修改目标。

## mock 能证明什么，不能证明什么

mock 是公开、有限的规则解析器，只识别README演示表达及用例覆盖的语法。它不返回预置业务结果，解析后的计划仍经过同一校验、图、固定 SQL 和真实 MySQL。因此它能帮助验证确定性工作流、SQL结果、接口合同以及错误分支，不能证明真实模型能理解任意中文。

live 使用配置的 Chat Completions 兼容接口，发送问题、支持范围及输出 schema，不发送数据库秘密或全表数据。支持供应商JSON输出能力时仍需本地校验，最多两次格式尝试共用有限总等待预算。网络、鉴权、限流、格式和超时分类，缺配置明确失败，不回退mock。

`/health` 不调用模型，以免健康检查触发费用。它检查配置和只读 MySQL 连接；即使返回健康，也不能当成真实模型成功调用的证据。真实模型调用和真实数据库验收需要分别记录。

## 怎样解释评测结果

评测包含16条固定语义用例：8条查询结果、4条澄清、4条拒绝。查询用例的标准计划和rows人工编写，金额精确比较，排名保留顺序，空结果同时检查计划和日期；第8条独立累加每日金额核对500.00。澄清和拒绝验证业务查询次数为零，不混进SQL结果正确数。新增的全句开始边界冲突与排除周末用例，也有模拟模型错误返回ready的零查询回归测试。

报告分开记录计划/状态通过数、查询结果正确数、非查询通过数、回答校验、错误分类和耗时。单元测试可替换模型或连接；MySQL集成测试必须启用真实MySQL8.4，不能用SQLite或跳过的检查替代。具体计数和通过情况应引用验收记录，而不是从测试文件存在推断。

这些固定用例不足以估计通用中文查询准确率，也没有建立性能基准或业务收益评估。本轮真实live已实际调用并接入MySQL：16条中计划/状态9条通过，8条查询结果5条正确，剩余失败主要为模型格式和超时；不能描述为live全部验收通过。具体逐条结果见 [live-verification.md](live-verification.md)，mock的16/16成绩不能替代它。

## 当前不支持的内容

任意Schema检索、自由SQL、任意附加筛选、退款、利润、预测、推荐、明细导出、同比环比、原因诊断、数据库管理和写操作均不在范围内。项目没有会话记忆、向量数据库、多Agent、任务队列、前端框架或生产身份认证。它展示的是一个小范围、权限受限、可审查的查询流程。
